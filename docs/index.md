# Blue Pill Bare-Metal

This documentation is the working guide for the STM32F103C8T6 Blue Pill
bare-metal project. It covers how the repository is organized, how to build and
flash firmware, and where to find the learning notes for startup, linker scripts,
memory maps, and peripherals.

The root `README.md` gives the short project overview. This page contains the
day-to-day project management details.

![Blue Pill board](assets/img-20260904-094011.png)

## Project Goal

The project builds small firmware examples for a Blue Pill board without
STM32CubeIDE. The point is to keep the hardware path visible instead of hiding it
behind generated code.

The main learning path is:

```text
reset
  -> vector table
  -> startup code
  -> linker-provided memory sections
  -> SystemInit
  -> main
  -> peripheral registers
```

Target hardware:

| Item | Value |
| --- | --- |
| Board | Blue Pill development board |
| MCU | STM32F103C8T6 |
| Core | ARM Cortex-M3 |
| Flash | 64 KiB official C8T6 size |
| RAM | 20 KiB |
| Debug/programming | ST-Link V2 clone over SWD |
| Onboard LED | Usually `PC13`, active-low |

## Toolchain

The project uses:

- `arm-none-eabi-gcc`
- `arm-none-eabi-objcopy`
- `arm-none-eabi-size`
- `arm-none-eabi-gdb`
- `make`
- `openocd`

STM32CubeIDE and official ST flashing tools are not required.

## Repository Layout

```text
.
├── Makefile
├── README.md
├── apps/
│   ├── bare-blink/
│   └── cmsis-blink/
├── asm/
│   └── startup_stm32f103c8tx.s
├── docs/
├── drivers/
│   └── cmsis/
├── include/
│   └── stm32f103c8t6.h
├── linker/
│   └── STM32F103C8TX_FLASH.ld
├── openocd/
│   └── bluepill.cfg
├── src/
│   ├── startup_stm32f103.c
│   ├── newlib_stubs.c
│   └── system_stm32f103.c
├── vendor/
│   └── STM32CubeF1/
└── build/
```

`apps/` contains one directory per application. `src/` contains shared runtime
code. `drivers/` contains reusable driver code for specific abstraction layers.
`include/` contains local direct-register headers. `asm/` contains reference
assembly that is not linked by default. `vendor/` contains pinned external
dependencies. `build/` is generated by `make` and should not be edited by hand.

## Vendor Submodule

`vendor/STM32CubeF1/` is a Git submodule pointing to ST's STM32CubeF1 repository:

```text
https://github.com/STMicroelectronics/STM32CubeF1
```

It is pinned to ST's official `v1.8.7` release tag.

After cloning this repository, initialize submodules with:

```sh
git submodule update --init --recursive
```

To update the working tree to the submodule commit recorded by the parent
repository later:

```sh
git submodule update --recursive
```

The submodule is not used by `bare-*` applications. It is only enabled for
applications that intentionally use the CMSIS layer.

## Application Layers

Application names describe the abstraction layer they use:

| Prefix | Meaning |
| --- | --- |
| `bare-*` | Direct-register examples using only local project headers |
| `cmsis-*` | Examples using CMSIS headers from the pinned STM32CubeF1 submodule |
| `ll-*` | Future STM32 LL-based examples |
| `hal-*` | Future STM32 HAL-based examples |

The Makefile keeps these layers separate. `bare-*` applications compile with
`-Iinclude` only. `cmsis-*` applications also get the STM32CubeF1 CMSIS include
paths and the device define `STM32F103xB`.

## Build

Build the default application:

```sh
make
```

The default application is `bare-blink`. To build a specific application, pass
`APP`:

```sh
make APP=bare-blink
make APP=cmsis-blink
```

Generated outputs for the default application:

- `build/bluepill-bare-blink.elf`
- `build/bluepill-bare-blink.bin`
- `build/bluepill-bare-blink.hex`
- `build/bluepill-bare-blink.map`

Clean generated files:

```sh
make clean
```

See [Build Process](build-process.md) for the detailed build explanation.

## Flash

Connect the ST-Link clone to the Blue Pill SWD pins:

| ST-Link | Blue Pill | Purpose |
| --- | --- | --- |
| `SWDIO` | `SWDIO` | Debug data |
| `SWCLK` | `SWCLK` | Debug clock |
| `GND` | `GND` | Common ground |
| `3.3V` | `3.3V` | Target reference or power, depending on setup |

Do not connect 5 V to a 3.3 V pin. The STM32F103 is a 3.3 V microcontroller.

Build and flash:

```sh
make APP=bare-blink
make flash
```

The flash target uses OpenOCD with the local board/probe config:

```sh
openocd -f openocd/bluepill.cfg -c "program build/bluepill-bare-blink.elf verify reset exit"
```

## Debug

Start OpenOCD:

```sh
make openocd
```

In another terminal, start GDB:

```sh
make debug
```

The GDB server listens on port `3333`.

## OpenOCD Config

The local config is:

```text
openocd/bluepill.cfg
```

It loads OpenOCD's installed ST-Link and STM32F1 target configs:

```text
interface/stlink.cfg
target/stm32f1x.cfg
```

The config also contains:

```tcl
set CPUTAPID 0x2ba01477
```

This was needed because this board/probe reported Cortex-M3 debug ID
`0x2ba01477`, while the default STM32F1 OpenOCD config expected a different
value.

## Active Firmware Pieces

`apps/bare-blink/main.c` is the first direct-register LED blink. It enables the
GPIOC clock, configures `PC13` as a 2 MHz push-pull output, and toggles the pin in
a delay loop. See [Bare Blink Application](apps/bare-blink.md).

`src/startup_stm32f103.c` is the active startup file. It provides the vector
table, reset handler, `.data` copy, `.bss` clear, and weak default interrupt
handlers. See [Linker And Startup](linker-startup.md).

`linker/STM32F103C8TX_FLASH.ld` defines the Flash and RAM layout:

```text
FLASH: 0x08000000, 64K
RAM:   0x20000000, 20K
```

`src/system_stm32f103.c` currently keeps the chip on its simple default clock
setup. It does not yet configure HSE, PLL, 72 MHz operation, flash wait states, or
bus prescalers.

`src/newlib_stubs.c` provides minimal Newlib syscall stubs for bare metal. Later,
implementing `board_putchar()` with UART will allow `printf()` output.
